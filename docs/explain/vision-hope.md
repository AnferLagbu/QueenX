# QueenX 期望目标

这是 QueenX 项目的期愿描述文档，非任务规划，仅记录长远期望与战略愿景。

## 核心定位

QueenX 是一个从零开发的自研操作系统内核，采用 framekernel 架构，以蚁后-蚁巢-工蚁的命名体系（QueenX 内核 / NestFS 文件系统 / AntX 发行版）体现项目的世界观。

项目的核心定位是 **专注内核深度**，不在用户态层投入精力与资源。

## 期望目标

长期目标是与 OpenHarmony **标准系统（standard）层的用户态空间**相结合，而**不是自建完整的 GNU/Linux 用户态**。路径判定只有一条：OH 的上层生态（应用框架、软总线、ArkUI、HUKS 安全子系统等）只存在于 standard 系统（用户态 musl + OH 组件，内核位为 Linux），因此 "OpenHarmony 兼容" 的实质是 **Linux 内核 ABI 的兼容度**——QueenX 仅需在 syscall 层做到足够 Linux，OH 用户态即可无感承载。这样 QueenX 可以避开用户态开发的巨大工作量，专心内核；同时获得生态环境的曝光度。small/mini 系统的 "替换 LiteOS" 形态不取：其应用直接静态链接内核 API、不存在独立用户态兼容面，且官方替换通道要求进基金会治理，与项目的独立姿态冲突。

最终呈现完整的 **蚁群世界观**：QueenX（蚁后内核）+ NestFS（蚁巢文件系统）+ AntX（工蚁发行版）+ OpenHarmony（外部生态）四方协同。形成一个完整的自研操作系统栈，既保持技术独立性又获得生态入口。

## 许可合规结论

QueenX 使用 OpenHarmony 用户态**无需任何授权**，依据分三层：

- **运行不触发许可义务** — 版权法不规制"运行"行为，Apache-2.0 第 3 条明确授予永久、全球、免版税的使用权；内核承载用户态二进制属执行独立程序（与发行版承载专有软件同理）。
- **许可体系互不传染** — OH 用户态主体为 Apache-2.0（含自带专利授权条款）与 MIT/BSD，QueenX 内核为 MPL-2.0；内核/用户态分界线是 GPL 家族公认的边界（Linux syscall 边界论证），两侧各自合规即整体合规。仅当 QueenX 分发**被修改的 OH 源码或 GPL 用户态组件**时，才触发对应组件自身的开源义务（保留版权头 / NOTICE / 修改声明），不波及内核。
- **唯一的真实边界是商标** — "OpenHarmony" 为开放原子基金会注册商标，合规姿态为描述性使用兼容关系，不自称本体、不暗示背书；代价是拿不到官方兼容性认证，而这正是独立性所求。

## 战略选择

**不开发完整用户态** — 仅开发部分用户态程序作为内核功能验证。用户态程序仅作为内核 e2e 测试用例，不追求通用性；不开发 shell、包管理器、桌面环境等 GNU/Linux 必备组件。

**借力 OpenHarmony 生态** — 不自建 GNU 兼容层，而是适配 OpenHarmony 用户态空间。相比自己拼一套完整的用户态，OpenHarmony 提供的整套上层空间更加务实。POSIX 接口的实现支持运行 GNU 软件是基础但非目标，真正目标是与 OpenHarmony 用户态无缝对接。

**兼容性自证，不进治理** — "与 OpenHarmony 无缝对接"不是申请来的资格，是做到足够 Linux 之后的涌现结果：验收形态是在 QueenX 上拉起 `init + 软总线 + ArkUI demo`（远期 QEMU 用例）。不走开放原子基金会的 SIG / 设备认证通道，兼容声明由实测证据自证；措辞上只作描述性使用（"兼容 / 可运行 OpenHarmony 用户态"），不自称 OpenHarmony 本体、不暗示官方背书（商标合规）。

**专注内核深度** — 将工程资源集中在内核子系统（调度/同步/文件系统/网络/安全/虚拟化）上。这是 QueenX 与绝大多数 OS 项目（都试图从内核到用户态完整自建）的差异点；通过生态对接而非自建完整用户态，实现 5-10 倍的工程效率提升。

## 哲学依据

**务实复用（ref-naming.md §4.2）** — 不重复造轮子，根据需求务实的借用既有生态，仅自研核心 TCB 与差异化部分。

**蚁群世界观** — QueenX（蚁后）统治 NestFS（蚁巢），AntX（工蚁）分发，OpenHarmony 是外部生态。生态系统中每个角色都有明确分工，内核不必全包全揽。

## 项目姿态愿景

QueenX 若成功与 OpenHarmony 上层结合，其项目姿态应**先将重心放在嵌入式与 IoT 场景**，而**以通用操作系统内核的姿态面向微计算场景**。具体含义：

- **场景重心**：嵌入式设备 / IoT 终端 / 工业控制 / 智能家居 / 边缘计算节点。这些场景计算资源有限但对实时性、可靠性、安全性要求高，与 QueenX framekernel 的安全模型 + NestFS 持久化 + 栏栈故障恢复高度契合。
- **姿态定位**：通用操作系统内核，而非嵌入式专用 RTOS。通用内核姿态意味着保留完整的 POSIX/Linux ABI 兼容能力、虚拟内存、进程隔离、文件系统等所有通用能力，仅在资源受限时裁剪或优化；不因嵌入式场景而牺牲内核的通用性。
- **微计算聚焦**：微计算（micro-computing）是嵌入式与 IoT 的本质特征 — 算力低、内存小（MB 级）、存储小（MB-GB 级）、网络间歇性强。QueenX 内核应针对这些约束做轻量化优化（小内存 footprint、低功耗 idle、低带宽容忍），但不放弃通用内核能力。
- **与 OpenHarmony 的契合**：OpenHarmony 本身面向的就是 IoT 与嵌入式设备，其标准系统的上层（ArkUI、软总线、HUKS 等）全部由用户态自供，内核暴露面很薄——图形起步只需 framebuffer/ramfb 映射 + evdev 输入 + 共享缓冲原语（KMS 语义可推迟，3D 加速依赖厂商闭源 DDK、明确非兼容目标）；真正的内核补课集中在 IPC 与事件基础设施（binder / netlink / uevent）。QueenX 承载 OH standard 用户态后，可同时获得 framekernel 安全模型与 OpenHarmony 生态入口。
